# 日报增长口径与发布标签纠错

范围沿用用户已授权的日报故障修复：保留历史日报和快照，只改后续自动生成逻辑。

## 已确认的问题

- 相邻自然日的快照未必相隔 24 小时；11 月 2 日、3 日的实际间隔约 25 小时 3 分钟，生成器却显示 `24h 净增`。
- Hermes 的 GitHub Atom 订阅包含 `rc.N-v…`、`abandoned-rc.N-v…` 发布流程标签，其摘要是 attempt/autopublish/attemptRef 元数据，而非功能更新。
- Hermes 固定中文摘要宣称关注记忆和工具调用，并不能由每条订阅内容支持。

## 方案与选择

1. 继续人工逐期修订：无需代码，但问题会反复出现。
2. 统一快照净差口径并窄范围识别流程标签：无需网络请求或快照迁移，作为本次方案。
3. 新增采集时间元数据、逐条查询 Release API：可进一步区分发布与标签，但扩大数据结构及限流处理范围，留待独立需求。

## 行为

- 增长表、总 Star 表统一显示“两次快照净增”，保留对比日期和净差计算。说明实际采集间隔不保证为 24 小时；没有时间证据时不编造时长。
- FeedReader 仅在 GitHub 的 NousResearch/hermes-agent release URL、特定 rc 标签模式、JSON 风格流程摘要三者同时匹配时丢弃条目。摘要允许 HTML 包装、实体编码与上游截断。
- 相同名字但带正常发布说明的 RC、其他仓库、其他网站、普通 Hermes release/canary 均保留。
- Hermes 默认摘要不推断功能；canary 明示发布状态及功能变化待核验。该策略不是全面验证 GitHub Release 状态。
- 不改快照 schema、增量字段、历史报告、AIGCNEWS 策略或工作流时间。

## 验收

先通过回归测试复现相邻日期 24h 标签、流程标签混入及 Hermes 摘要问题，再实现修复。验证正负净差、基线及缺失数据行为不变；完整测试通过后重新同步远程、核验源码并发布。检查远端 main 与 staging 包含相同源码树，保留用户未提交内容。
